### 1. 从"能跑的代码"到"能演进的架构"

这个项目给我的最大冲击，是**同一份功能，两种写法，代价完全不同**。

项目初期的第二个星期，我写的第一版检测代码是一个大约 400 行的 `detect.py`：
读了摄像头，调 MediaPipe，写一堆 `if ear < 0.21:` 然后 `print("闭眼")`。
它能跑，甚至看起来效果不错。但当我试图加第三个、第四个行为检测时，
麻烦立刻出现了：

- 阈值散落在十几个地方，调一次要全局搜索；
- 想加"连续 5 帧才算"就得分七个地方各写一遍计数器；
- 想测试"低头 20 度会不会误报"，必须开摄像头、自己低头——无法自动化；
- 想把 MediaPipe 换成别的库，等于重写。

那 400 行代码的功能，和最终交付的 `src/driver_guard/` 下的代码功能是一样的，
**差别在于前者只能演示一次，后者可以被修改一百次**。这就是"架构"这个词
对我来说从抽象概念变成具体价值的那一刻。

具体地说，我做了三个当时觉得"过度设计"、后来证明是救命的设计：

| 当时觉得多余的设计 | 后来的回报 |
| :--- | :--- |
| `domain/` 层禁止 import 任何外部库 | 247 个测试用例可以在没有摄像头、没有模型、没有显示器的环境下 1 秒内跑完。**项目中有 5 个真实缺陷，3 个是这个选择抓到的** |
| `application/ports.py` 定义接口，具体实现放 `infrastructure/` | 答辩现场如果没有摄像头，一条命令 `--source replay --provider replay` 就能完整演示；甚至可以在断网的笔记本上跑 |
| 所有阈值外置到 `config/default.json` | 现场调整灵敏度不需要改代码、不需要重跑测试；`AppConfig` 还做了范围夹紧和未知键告警 |

### 2. 关于"时间是一条数据"的领悟

我原来以为"可测试性"就是"多写点单元测试"。这个项目让我明白，
**可测试性首先是架构性质，其次才是写测试的努力**。

最直接的例子是时序判定。规则要求"持续 1.2 秒以上才告警"。如果代码里写
`time.time()` 或 `time.sleep()`，测试就只能真的等 1.2 秒——一组时序测试
就要跑十几秒，而且偶发失败（CI 机器负载不同）。我们最终的方案是把
`timestamp` 作为**参数**传进确认器，测试传入假时钟：

```python
# 测试中的"时间旅行"——不真实等待，而是直接给时间
clock.advance(1.5)
outcome = confirmer.update(rule_outcome, timestamp=clock.now())
```

整个行为确认器的 11 个测试用例（含迟滞、冷却、单帧丢失容忍）跑完不到 10 毫秒，
而且**结果 100% 确定**。这件事让我第一次真正理解"时间作为数据"
（time as data）这个说法——它不是设计模式的优雅，而是**可测试性的前提**。

后来我在评审文档里把它写成了 SP-9 与 S-23：**如果一个模块读系统时钟，
它就已经不可测试了。**

### 3. 最大的挫败：头姿判定的"绝对角幻觉"

这是整个项目里我印象最深、也最狼狈的一段。

按教科书和大多数博客的写法，判断"是否低头"就是：

```python
if pitch > 20:   # 低头超过 20 度
    alert()
```

我们照做了，写得很开心，还画了漂亮的三轴旋转矩阵分解。然后在真实人脸
图片上测试时发现：**同一个人，只是把摄像头往下掰了 5 度，pitch 就整体偏移了
十几度**；换一个人坐姿略微前倾，也偏移。更糟的是，我用不同图片做对照实验时，
发现 MediaPipe 返回的旋转矩阵**根本不符合我预想的 OpenCV 相机坐标约定**——
它的 X/Y/Z 轴朝向和相机坐标系不是同一套。官方文档里没有清楚的说明。

那一刻我才意识到：我在用一个**语义不明的量**做阈值判断。
哪怕阈值调得再好，只要换一个摄像头安装角度、换一个驾驶员身高，
它就完全失效——而这两个变量在实际使用中**必然会变**。

我花了两天做两件事：

**第一件，验证数学性质是否可靠。** 我写了 18 个参数化测试，专门检查
`euler(Δ ⊗ R) ≈ euler(R) + Δ` 这个关系（左乘一个小旋转 Δ 相当于在欧拉角上
加一个偏移量），结论是：|角度| ≤ 30° 时误差 < 2°，而且 `euler_to_matrix` 与
`rotation_matrix_to_euler` 的往返精度达到 1e-9。**也就是说，变换本身没问题，
出问题的是"绝对方位"的解释。**

这个结论非常关键——它让我知道问题不在我的代码，而在于我把一个**相对量**
当成了绝对量用。

**第二件，改架构。** 我们定下 ADR-05：

1. 姿态角只作为**相对量**使用，一律判定"相对于该驾驶员中立位的偏离"；
2. 会话开始时自动标定个人中立位（用**中位数**估计，抗离群）；
3. **再加一条与轴系完全无关的判据**：眼睛中线到嘴中线的纵向距离 ÷ 脸宽。
   低头时因为透视压缩，这个比值会下降。它不依赖任何旋转矩阵；
4. 标定未完成时，头姿规则**跳过**而不是用固定阈值兜底。

改完之后效果立竿见影：阈值反而可以调得更紧（因为基准已经扣掉了个体差异），
灵敏度与特异度同时改善。而且因为有了"双证据通道"，即使其中一个通道失效，
另一个还能工作。

**这件事教给我的方法论是**：当你依赖一个第三方库的输出时，**先验证它的
数学性质，再假设它的物理语义**。数学性质是库作者会测试和保证的；
物理语义经常取决于约定，而约定经常没有写在文档里。

我也把这次教训写进了评审文档——它是风险 R-2 的实证，而不是我事后
编出来的"我们考虑过这个风险"。

### 4. 关于"缺陷分布"的观察

项目结束时我统计了一下发现的 5 个真实缺陷（详见评审文档 6.2 节）：

| 缺陷 | 发现方式 | 严重度 |
| :--- | :--- | :---: |
| 取消订阅失效（订阅泄漏） | 单元测试 | 中 |
| **低头规则每帧误报** | **离线门禁脚本** | **高** |
| 记录中的指标被标志位覆盖 | 端到端冒烟测试 | 中 |
| "只提供指标的感知实现"被判为无驾驶员 | 单元测试 | 中 |
| 回放模式数据源永不结束 | 全量测试执行（进程"不进展"） | 中 |

其中**三个是自动化测试发现的**。最后一个尤其有意思：它没有报错、
没有堆栈，只是"不进展"——一个默认值为 0 的"无限时长"参数，
让回放模式的主循环永远读得到新帧。修法也不是在测试里绕过去，
而是让组合根把"回放脚本本身有长度"这个领域知识用来约束数据源。

第二个缺陷值得单独说。它的成因是一个**负号**：配置文件里写着
`pitch_threshold_deg: -18.0`（早期"负值代表低头"的设计残留），
而规则是拿"偏离幅度"去比较的，`0 > -18` 永远成立。后果是
**系统对任何驾驶员都持续误报低头**——核心质量属性"零误报"完全失效。

发现它的是我写的一个小工具 `tools/probe_scenarios.py`：它把 6 条离线脚本
全部跑一遍流水线，断言每条脚本产生的告警集合恰好等于预期。第一次跑，
`normal`（正常驾驶）脚本报出了 4 次低头告警，867/900 帧瞬时命中。

这让我明白两件事：

1. **"零误报"这种质量属性必须有可执行的门禁，不能靠肉眼观察**。
   如果只靠人工演示，这个缺陷会在答辩当天才暴露；
2. **跨边界的语义不一致（配置的语义 ↔ 代码的语义）是类型系统抓不到的**。
   这类缺陷只能靠"可执行的契约检查"防御。

所以我把 `probe_scenarios.py` 固化成了交付前必跑的门禁，并在评审文档里
把它列为整改项 A-5。

### 5. 对"架构评审"的理解转变

在写架构评审文档之前，我以为 ATAM 就是"填几个表格"。真正做下来才发现，
效用树、敏感点、权衡点、风险点这四个东西其实是**四种不同的问题**：

| 概念 | 回答的问题 | 例子（本项目） |
| :--- | :--- | :--- |
| 敏感点 | 哪个参数变化会显著影响某个属性？ | 滑动窗口长度：越长越不误报，但告警越迟 |
| 权衡点 | 哪个决策让两个属性**对着干**？ | 灵敏度 vs 误报率；同步分发 vs 可扩展性 |
| 风险点 | 什么可能让我们做不到？ | MediaPipe 轴系不明（已兑现）；无真实数据（残余风险） |
| 非风险点 | 什么看起来危险其实不危险？ | 用 numpy 跨线程传数组（纯内存对象，无 Qt 线程亲和性问题） |

写"非风险点"这一节特别有意思。它逼着我为每一个"没当回事"的决策
**给出理由**——如果给不出理由，那它其实就是风险，只是我还没意识到。

另外我在评审文档 1.2 节专门写了"评审局限"，明确说明：没有真实驾驶数据、
没有车队管理员参与、只有一位驾驶员访谈。我觉得这比假装评审很全面要诚实，
也更有用——评审的价值在于让别人知道"哪些结论可以信、哪些不能信"。

### 6. 团队协作方面的体会

三个人、六周、文档和代码并行，我的主要体会是：

- **接口先行**：我们第一周就定下了 `Observation` / `DriverMetrics` /
  `RuleOutcome` / `BehaviorEvent` 四个值对象和四个端口的签名。之后三个人
  各自写规则、写界面、写文档，几乎没有互相阻塞。**先吵架把接口吵清楚，
  比后来改接口便宜一百倍。**
- **口径统一比代码统一重要**：比如"可空"的含义。早期有争议——指标缺失时
  是填 0 还是填 `None`？我们最终定为"**保持 `None`，可空即不可用**"，
  并把它写成架构不变量 INV-6。这个决定后来救了我们：如果填 0，
  降级模式下 EAR 缺失会被读成"闭眼"，必然持续误报。
- **把"演示"当成一个需求**：我们有一份专门的离线脚本库（6 条有限长度脚本）
  能在无摄像头环境下驱动全链路。这不是"额外的演示代码"，
  而是可用性需求 S-11 的架构应对——它同时在开发期作为回归门禁使用。

### 7. 如果重做一次

我会：

1. **第一天就写 `probe_scenarios.py`**。它是整个项目性价比最高的 150 行代码；
2. **对每一个第三方库的输出先写"性质测试"，再写业务逻辑**。头姿那两天

3. **更早定义"什么算完成"**。我们第三周才明确"零误报"是可度量的验收条件

### 1. 设计模式：从"背名字"到"解决问题"

上课时我背过 23 种设计模式的名称和 UML，总觉得它们是"为了让代码好看"。
这个项目让我明白：**模式的价值取决于你有多少种变化维度。**

举两个具体例子。

**策略模式（Strategy）——感知实现的替换**

```python
class LandmarkProvider(ABC):
    @abstractmethod
    def infer(self, frame: Frame) -> Observation: ...
```

我们写了三个实现：MediaPipe（主力）、Haar 级联（降级）、回放脚本（演示/测试）。
最有意思的是 Haar 那个实现：它其实**不做人脸关键点检测**，只是用眼睛级联
判断"眼睛是否睁开"，然后把结果映射到眨眼系数通道上。

它居然能正常驱动闭眼疲劳规则——**规则完全不知道数据是来自 478 点的人脸网格
还是来自一个 Haar 级联**，因为它只消费 `DriverMetrics` 这个值对象。

那一刻我才真正理解"策略模式"是干什么的：它不是"把 if-else 换成类"，
而是**让调用方对实现完全无知**。

**微内核 + 插件——规则的可插拔**

我们的 `RuleEngine` 是一个很"瘦"的微内核：它只负责调度和容错，
一行业务阈值都没有。7 条规则是插件：

```python
RULE_FACTORIES = {
    "eyes_closed": EyesClosedRule,
    "yawning": YawningRule,
    # 新增一条规则，这里加一行
}
```

我算过新增一种行为的成本：领域枚举 +3 行、新规则类 ~40 行、注册 +1 行、
配置 +10 行——**既有文件改动 0 处**。这就是开闭原则的实际含义。

**模板方法（Template Method）——流水线骨架**

`DetectionPipeline.process()` 是一帧数据的主流程骨架，
每一步都留了钩子 `_perceive()` / `_measure()` / `_build_context()` / `_confirm()`。
基类实现了"计时 + 异常兜底 + 组装 `FrameAnalysis`"这些横切关注点，
子类只需要关心各步做什么。

第四个钩子 `_confirm()` 的存在是因为我们做了 ADR-03 的重构：把"连续 N 帧"
从规则里抽出来。抽取之前，7 条规则各自实现计时；抽取之后，
时间域逻辑只存在一份。

**我的结论**：模式不是"用得多就好"。我们最终用了 16 处模式，
但每一处都能对应一个具体的变化维度。评审时如果有人问"你为什么用这个模式"，
我们应该能答出"因为这里会变的是什么"——答不出来，就说明这个模式是多余的。

### 2. 吃过的亏：几个具体的技术坑

这个项目里我踩的坑，我愿意都写下来，因为每一个都花了真金白银的时间。

**坑 1：MediaPipe 1.0.1 删掉了 `mp.solutions`**

按网上绝大多数教程的写法：

```python
mp_face_mesh = mp.solutions.face_mesh        # AttributeError!
```

我一开始以为是安装坏了，重装了三次，查了半天才确认：
**1.x 版本已经移除了旧的 `solutions` API，只有 `mediapipe.tasks`**。

新 API 的写法完全不同：

```python
from mediapipe.tasks import python as mp_python
from mediapipe.tasks.python import vision
base = mp_python.BaseOptions(model_asset_path="face_landmarker.task")
landmarker = vision.FaceLandmarker.create_from_options(options)
result = landmarker.detect_for_video(mp_image, timestamp_ms)  # 注意时间戳
```

而且模型文件（`.task`）**需要自己下载**，不像旧版 API 是内置的。
我们写了 `tools/download_models.py` 一键解决。

**教训**：教程的时效性可能只有几个月。遇到 API 不存在时，
第一件事是查装的那个版本的文档，而不是怀疑环境。

**坑 2：`detect_for_video` 要求时间戳严格单调递增**

这个坑更隐蔽。它报的错是：

```
ValueError: Input timestamp must be monotonically increasing
```

原因是我们用 `int(time.time() * 1000)` 当时间戳。回放模式下帧率极高，
同一毫秒内会调用好几次 `detect_for_video`，时间戳相等 → 报错；
更糟的是视频循环播放时时间会"回绕"，时间戳反而变小 → 报错。

解决方案是维护一个**与墙钟无关的独立递增计数器**：

```python
def _next_timestamp_ms(self) -> int:
    self._timestamp_ms += self._frame_interval_ms   # 只增不减
    return self._timestamp_ms
```

**教训**：给推理库的时间戳是**序号语义**，不是墙钟语义。
把这两者混在一起用迟早出事。

**坑 3：OpenCV 5.0 不再附带 Haar 级联 XML**

这个坑最让我意外。教科书式的代码：

```python
cascade = cv2.CascadeClassifier(
    cv2.data.haarcascades + "haarcascade_eye.xml"
)   # 文件根本不存在，cascade.empty() == True
```

安装目录下设 `cv2.data.haarcascades` 指向的文件夹里**只有一个 `__init__.py`**，
没有任何 XML。而且 `CascadeClassifier` 加载失败时**不抛异常**，
只是对象变"空"，后续 `detectMultiScale` 静默返回空列表——
你会以为"这个人没睁眼"，而不是"分类器没加载"。

我们的应对：写 `tools/fetch_cascades.py` 下载，并在 provider 里提供
`missing_files()` 方法，启动时给出**包含修复命令的提示**，
而不是让用户面对一个"什么都不检测"的程序。

**教训**：**静默失败比崩溃危险得多**。任何可能静默失败的地方，
都应该有一个显式的"就绪性检查"。

**坑 4：`cv2.warpPerspective` 的矩阵方向**

这个是几何测试里发现的。`warpPerspective(src, M)` 实际算的是
`dst(x) = src(M·x)`，所以如果你用 `M` 表示"图像旋转了 R"，
那么从"原始图像"到"看起来的样子"用的其实是 `M⁻¹`。
我在测试里发现数值对不上，查了好一会儿才想明白矩阵方向被反了。

**教训**：不要在脑子推演矩阵方向，直接写一个往返测试。

**坑 5：一个忘掉的赋值导致订阅永远无法取消**

这个 bug 让我对"依赖注入"有了新的敬畏。代码大致是这样：

```python
def subscribe(self, topic, handler):
    sub = Subscription(handler)
    self._subs[topic].append(sub)
    return sub

class Subscription:
    def __init__(self, handler):
        self._handler = handler
        self._bus = None          # 忘了回填！

    def close(self):
        if self._bus is None:     # 永远为真 → 直接返回
            return
        self._bus._remove(self)
```

看起来完全正常的代码，`close()` 是个**静默的空操作**。
后果是：服务停止后订阅还在，下次会话又注册一遍，告警会被重复输出，
而且 `StatisticsService.close()` 也失效。

是单元测试抓到的——3 个用例失败，而且失败信息很直接
（"关闭后仍收到回调"）。我加了一句 `sub._bus = self` 就好了，
然后补了 9 个用例覆盖订阅生命周期。

**教训**：**双向引用/生命周期管理必须有测试**。这类缺陷在人工点几下
界面的测试方式下**永远不会暴露**（因为栈上没有报错，界面看起来也正常）。

**坑 6：一个"不会结束的循环"比报错更难查**

这个坑发生在项目收尾阶段，代价是整整一次全量测试运行的时间。
现象是：跑 `pytest` 的时候，前 58% 的用例很快就绿了，然后**整个进程就不动了**——
没有报错、没有超时、没有任何输出，只是"不进展"。

定位之后发现根源很朴素：合成数据源的时长参数 `synthetic_duration`
默认值是 `0`，含义是"无限"——这对摄像头式数据源是合理的（一直播），
但**对"回放脚本"这种本来就有长度的数据源毫无意义**。于是回放模式下
`run()` 的主循环永远读得到新帧，永不返回。

它的代价链条是：

1. 集成测试里的场景门禁跑不完 → 整个测试进程挂住；
2. 会话汇总永远产出不了 → 回放演示拿不到"本次会话报告"；
3. 任何脚本化验证（`--no-gui`）都必须额外记得加 `--max-frames`，否则挂住。

整改方案不是"在测试里加个 `max_frames` 绕过去"，而是**把领域知识交给组合根**：
回放脚本本身有长度，那么"回放模式的数据源长度"就应该默认对齐脚本长度。
于是新增了一个 `scenario_duration()` 查询函数，并让 `create_frame_source()`
在**未显式配置时长**时自动对齐（显式配置为正数仍然表示"无限循环播放"，
保留了演示时循环播放的能力）。

**两条教训**：

1. **同一个配置字段在不同上下文下语义不同，就应该被显式区分或给出默认对齐**。
   `0 = 无限` 单独看没问题，但"回放脚本 + 无限"就是自相矛盾；
2. **"不结束"比"崩掉"贵得多**。崩溃会给你栈；不结束只给你沉默。
   所以带循环的代码路径都应当有可观察的进展信号，测试也不应无限期等待。

### 3. 关于线程：界面的"静默卡顿"

我们最初把检测循环和界面放在一个线程里。结果就是：拖动窗口、
切换标签页的时候，检测帧率明显下降——因为界面消息循环被检测阻塞了。

分离成两个线程后好多了，但立刻遇到 Qt 的约束：**`QPixmap` / `QWidget`
只能在 GUI 线程创建**。跨线程传 Qt 图形对象会随机崩溃或花屏——
而且是"随机"，本地可能十次都不复现，答辩时复现一次就完了。

我们的规则是：**跨线程只传纯数据**。工作线程发 numpy 数组（`object` 类型的信号），
到了界面线程才转成 `QImage` / `QPixmap`。

另一个坑是**停止信号不能走事件循环**。工作线程的 `run()` 是一个长循环，
它的线程事件循环根本没在跑，所以用"队列连接"（QueuedConnection）投过去的
`stop()` 槽永远不会被处理，点"停止"按钮没反应。
解决办法是界面线程**直接调用** `worker.stop()`（普通方法调用是线程安全的，
因为内部用的是 `threading.Event`），主循环在下一轮检查到标志位就退出。

**教训**：Qt 的线程模型有硬约束，不能靠"应该没问题"来写。
把约束写成不变量（我们的 INV-4），并在代码注释里写明原因。

### 4. 关于性能：先测量，再优化

我一开始想了很多优化方案：多线程推理、降采样、只检测感兴趣区域……
后来我们写了 `tools/benchmark.py` 做分阶段埋点，实测结果是：

| 阶段 | 耗时 |
| :--- | :--- |
| F1 感知（MediaPipe 推理） | **占绝大部分** |
| F2 度量 | < 1 ms |
| F3 决策 | < 1 ms |
| F4 确认 | < 1 ms |

F2~F4 合计纯处理吞吐超过 1000 FPS。**瓶颈唯一地集中在感知阶段。**

这个数据直接改变了我们的优化方向——不再是"优化算法"，
而是"把感知放到独立线程"（保证界面不拖累它）、"提供隔帧推理开关"（低配兜底）、
"把 UI 渲染移出采集链路"（保证不反向拖累）。

如果我们凭感觉去优化领域层的计算，会花很多时间在没有收益的地方。

**教训**：**性能问题的第一件事永远是定位瓶颈，而不是优化**。
我们还专门把"分阶段埋点"这个决策写进了 ADR——因为它不只是个工具，
它决定了"实时性"这个质量属性是否可被验证。

### 5. 关于"可空，而不是 0"

这是我们讨论最久、也最有价值的一个约定。

`DriverMetrics` 的每个字段都允许是 `None`。含义是"**这条证据通道当前不可用**"
（被遮挡、侧脸、降级模式、模型缺失）。

一开始有人提议"缺失就填 0，简单"。但想一下后果：

- `ear = 0.0` 会被 `EyesClosedRule` 读成"眼睛完全闭上" → **必然持续误报**；
- `hand_face_ratio = 0.0` 会被打电话规则读成"手紧贴着脸" → **同样误报**。

如果保持 `None`，规则就能正确地跳过或切换到其它证据通道。
这条约定后来成了架构不变量 INV-6，还在评审文档里作为"降级设计"的关键。

**教训**：**数据模型里的 `null` 不是"没有值"，而是"有一个已知的、不同的事实"**。
用 0 代替 `None` 是把两种不同的事实混淆了。

### 6. 收获的一句话总结

> 这个项目让我明白：**写得快不等于写得好，能改才对**。
> 16 处设计模式、4 层分层、8 条架构不变量，最终换来的东西很简单——
> 当需求变化时，我知道该动哪个文件。

### 1. 测试不是"最后补的"，而是架构的一部分

接手测试这块的时候，我以为就是"写点用例覆盖一下"。真正做下来之后，
我的理解变了：**我们能有 100+ 个秒级跑完的测试，是前面架构决策的结果，
不是测试努力的结果。**

具体说，测试能这么轻松的原因有三个，全都在架构里：

| 架构决策 | 对测试的直接好处 |
| :--- | :--- |
| domain 层零外部依赖 | 测规则不需要 MediaPipe、不需要 Qt、不需要摄像头；import 就完事 |
| 时间作为参数传入 | 测"持续 1.2 秒"不需要真的 sleep 1.2 秒；测试跑 10 毫秒 |
| 端口可被替身实现 | 用 `ReplayLandmarkProvider` 精确控制每一秒的指标值，测试变得完全确定性 |

所以我在测试文档里写的第一句话是：**"可测试性（S-22~S-25）是架构属性，
不是测试工作量。"**

### 2. 我在写测试时踩的坑：测试自身也会写错

这个必须诚实说。项目中期有一次跑测试，6 个失败，我很兴奋地跑去
"报告 bug"。组长看完之后说："其中 3 个是你的测试写错了。"

具体是三种情况：

**情况一：夹具偷偷帮我设好了中立位**

我们的规则里，"低头"是判定**相对中立位的偏离**。我的测试夹具
`context_factory` 默认会带上一个中立位 `NeutralProfile`，
所以我构造了 `pitch = -25` 想测"极端低头"——结果相对偏离只有 20 度，
刚好在阈值边缘，测试不稳定。

正确的做法是让夹具支持不带中立位：我加了 `with_neutral=False` 参数，
测试里显式控制。

**教训**：**夹具做得太"贴心"会掩盖真实行为**。夹具应该让测试意图
显式表达，而不是偷偷补上默认值。

**情况二：我误解了 `release_frames` 的语义**

我写了一个测试断言"出现一帧不成立就立即清零计时"。测试失败，
我以为是代码 bug。实际上代码的设计是：**要连续 `release_frames` 次
不成立才清零**，这样能容忍单帧的关键点丢失。

代码是对的，我的断言错了。后来我们把这个语义正式写进了文档和
测试名称（`test_single_dropout_is_tolerated`）。

**教训**：**测试失败时，先怀疑自己对需求的理解，再怀疑代码。**
而且一旦确认了语义，就应该把它写成**名字自解释的测试**——
测试名本身就是规格说明。

**情况三：我构造的离群值太离群**

测"中位数抗离群"时，我在 30 帧基准里塞了一帧 `pitch = 80°`。
结果标定后的基准偏了好几度，测试失败。

原因是代码里有一道**守卫**：`max(|pitch|,|yaw|,|roll|) > 35°` 的帧会被
直接丢弃（因为那不是"中立位采样"，而是明显在转头）。我的 80° 帧
被丢掉了，所以它**根本没起到"离群"的作用**，反而是剩下的帧数不够。
我把离群值改成 20°（在守卫范围内但相对其余帧明显偏离），测试就通过了。

**教训**：**测试数据必须落在被测逻辑的"有效输入域"内**，
否则测的不是你想测的东西。

### 3. 测试替身抓到的真 bug

这是我最想分享的一点：**我写的测试替身抓到了 3 个只有它有本事抓到的
生产 bug。**

| bug | 为什么人手点界面抓不到 |
| :--- | :--- |
| 取消订阅失效 | 界面看起来完全正常，栈上也没有报错；只有"关闭后仍在收到回调"的**断言**才能发现 |
| 指标被标志位覆盖（`MAR` 显示成 `1.0`） | 界面显示的是"打哈欠 76%"这类加工后的信息，`1.0` 被掩盖了；只有断言"记录里的数值必须等于输入数值"才能发现 |
| "只提供指标的感知实现"被判为无人 | 主力感知实现总是产生关键点，所以主路径上永远不触发；只有用"只给指标的替身"测才能暴露 |

特别是第二个。这是最典型的"**只有断言能抓**"的缺陷——
在界面上你看不出任何异常，它安静地把真实测量值 `0.72` 覆盖成标志位 `1.0`。
如果这些数据被拿去做事后人工复核，就是在读假数据。

**结论**：**测试替身不只是"假的实现"，它是"能构造出真实世界难以复现的
条件的装置"**。回放感知让我们能精确控制"第 12 秒 EAR 降到 0.12"，
这在真实摄像头上做不到。

### 4. 端到端门禁：150 行代码，最高性价比

如果让我推荐这个项目里最值得先写的东西，我会说
`tools/probe_scenarios.py`。

它的逻辑很简单：

1. 定义 6 条离线脚本（正常 / 疲劳 / 分心 / 违规 / 离位 / 综合），
   每条是"在某个时间段内指标取某些值"；
2. 定义每条脚本**应该**产生哪些告警（以及 `normal` 应该产生**零**告警）；
3. 跑完整流水线，断言实际告警集合 == 预期；
4. 退出码作为门禁。

它抓到的最严重的缺陷（评审文档里的 D-2）：配置里一个**负号**
导致低头规则恒真，`normal` 脚本出现 4 次误报、867/900 帧瞬时命中。

**这个缺陷为什么危险？**

- 单元测试抓不到：单元测试各自测单条规则，而"全局误报率"需要**端到端**才能看到；
- 人工演示可能抓不到：如果你碰巧演示的时候没人低头，可能看起来正常；
- 但它意味着：**任何驾驶员只要正常坐着，系统就会一直报警**。
  核心质量属性"零误报"完全失效——这是产品级的失败。

**教训**：**质量属性（"零误报"）必须有端到端、可执行的门禁，
不能靠"看起来没问题"。** 单元测试保证"部件对"，
端到端门禁保证"整体对"，两者缺一不可。

### 5. 关于写文档的体会

我负责的四份文档（需求、架构设计、架构评审、心得体会）加上背景说明，
总计约 8 万字。写完最大的体会是：**文档和代码必须能互相验证**。

我在需求文档里做了一件自己觉得最有价值的事：**完整的需求追溯矩阵**。
63 条功能需求、20 条质量需求、14 条限制条件，逐条对应到：

| 需求 | 架构元素 | 实现位置 | 验证方式 |
| :--- | :--- | :--- | :--- |
| FR-C-03 闭眼疲劳检测 | 管道 F2 度量 + F3 决策 | `domain/rules/fatigue.py::EyesClosedRule` | `test_domain_rules.TestEyesClosedRule` |
| ... | ... | ... | ... |

做这个矩阵的过程非常痛苦，但它带来了两个真实收益：

1. **发现了两条需求没有落点**——写矩阵时才意识到"打哈欠的个体差异适配"
   我们其实没做，于是补进了技术债而不是假装它存在；
2. **评审时可以直接抽查**——审查者任选一条需求，我可以立刻说出
   "在哪个文件、由哪个测试保证"。这比说"我们都实现了"有说服力得多。

另外我在写架构评审文档 1.2 节时专门写了**评审局限**：
没有真实驾驶数据、干系人覆盖不全、人因样本量不足。
一开始我觉得"写局限是不是显得自己做得不好"。后来想通了：
**没有局限说明的评审结论是不可信的**。清楚地说明"哪些结论不能信"，
比含糊地说"总体满足"更有专业价值。

### 6. 关于"零误报"这个质量属性

课程里讲质量属性时，我感觉"性能""可靠性"这类词很抽象。
这个项目让我第一次把一个质量属性量化到可验证：

| 项 | 内容 |
| :--- | :--- |
| 质量属性 | 可靠性 → 误报抑制 |
| 场景 | S-5：正常驾驶 30 秒（含眨眼、说话、转头） |
| 响应度量 | 确认告警数 = 0 |
| 验证方式 | `python tools/probe_scenarios.py`，退出码 0 |
| 违规后果 | 用户会关闭系统 → 所有功能失效 |

把它写成这样之后，测试就变得非常明确：不需要讨论"准确率够不够高"，
只需要问"退出码是不是 0"。

**教训**：**质量属性如果不可度量，就不可验证；不可验证就不可保证。**

### 7. 团队协作中的"文档即接口"

三个人并行工作时，文档不只是"最后的作业"，它也是**接口**。

我们最有效的一个做法是：**值对象先定，实现后写**。
第一周我们就定死了四个核心数据结构（`Observation` / `DriverMetrics` /
`RuleOutcome` / `BehaviorEvent`）的字段和语义。之后：

- 我写测试时直接按这些字段构造数据，不需要等实现；
- 开发负责人写规则时按这些字段读数据；
- 组长写界面时按这些字段显示数据。

中间只改过一次接口（把"时序确认"独立出来，见 ADR-03），
改动波及面也完全可控（因为字段本身没变，只是谁负责填计时的问题）。

**教训**：**先定数据结构，再并行开发。** 数据结构是并行工作的最小公约数。

另外我们对"可空"这件事的讨论让我印象很深。我一开始在测试里
把缺失的指标填 0，被开发负责人指出这会让规则必然误报。
改成 `None` 之后，我需要重写一批测试——但这批测试反而更好写、
更接近真实场景（真实失败模式就是"某个通道不可用"）。

### 8. 如果重做一次

1. **第一天就建好测试骨架和端到端门禁**，不要等到第 3 周；
2. **把"边界值"专门列一类测试**（阈值恰好等于、恰好差一点、
   负值配置等），因为 D-2 说明阈值类 bug 的代价特别高；
3. **每个架构不变量都配一个可执行检查**（不变量 INV-1~INV-8 里，
   目前只有部分有自动检查，其余靠代码走查）。

### 9. 收获的一句话总结

> **测试不是"证明代码没问题"，而是"让我知道我今天想错了什么"。**
> 这个项目最让我有成就感的时刻，不是测试全绿，而是 6 个测试变红之后，
> 我们发现自己抓到了一个会导致系统对所有人误报的负号。

## 四、共同的体会（三人讨论后汇总）

### 4.1 我们真正学会的三件事

| # | 体会 | 具体证据 |
| :---: | :--- | :--- |
| 1 | **架构的价值体现在修改成本上，而不是图上** | 新增一种危险行为 = 0 处既有代码修改；换感知实现 = 0 处领域层修改；改灵敏度 = 0 处代码修改 |
| 2 | **质量属性必须可度量、可执行、可门禁** | "零误报" = 退出码 0；"无硬件可测" = 247 个用例无摄像头跑通；"实时性" = 分阶段埋点 + `benchmark.py` |
| 3 | **不要相信未经验证的语义，先验证性质** | 头姿角的绝对方位不可靠（ADR-05）；MediaPipe 时间戳是序号不是墙钟；OpenCV 5 不再附带级联 |

### 4.2 我们承认的不足

| 不足 | 影响 | 后续方向 |
| :--- | :--- | :--- |
| 没有真实驾驶视频的定量精度评估 | 无法给出准确率/召回率；不能用于考核处罚 | 采集并标注真实数据，建立混淆矩阵（TD-1） |
| 干系人覆盖不全（无车队管理员） | 运维/可维护性结论基于团队自判 | 补充访谈与实地测试 |
| 部分架构不变量只有"走查"没有"自动检查" | 依赖人的纪律 | 为 INV-4、INV-7 编写自动化检查脚本 |
| 手部判据用二维归一化距离 | 侧脸/手在脸后方可能误判 | 引入关键点 z 做三维距离（TD-2） |
| 未覆盖"双手离把""未系安全带" | 功能覆盖不全 | 需增加区域检测模型（TD-3、TD-4） |

### 4.3 对"软件体系结构"这门课的理解变化

| 上课之前 | 做完项目之后 |
| :--- | :--- |
| 架构就是分层和画图 | 架构是**决策的集合**，每个决策都要能回答"为什么这样选、反过来会怎样" |
| 设计模式是名词表 | 模式是**变化维度的封装**；答不出"这里会变什么"，模式就是多余的 |
| 质量属性是形容词 | 质量属性是**带度量、带场景、带门禁的验收条件** |
| 测试是编码之后的事 | 可测试性是**架构选择的结果**；架构不配合，测试写不动 |
| 文档是交付材料 | 文档是**团队的接口契约**（值对象先定，实现后写） |
| 风险是"注意一下" | 风险是**登记、评估、缓解、跟踪状态**的工程活动（本项目 H 级风险 3 项全部闭环，其中 2 项是真实兑现的） |

### 4.4 结语

这个项目的技术规模不大——它检测 7 种行为，跑在一个摄像头和一个界面上。
但它完整地走了一遍架构活动：从需求与质量属性的提取，到驱动力的识别，
到样式与模式的选择，到 ADR 的记录，到质量场景的度量，到 ATAM 式的评审，
到风险的兑现与整改闭环。

我们最大的收获不是"做出了一个能检测危险行为的程序"，
而是**知道了为什么它是这样写出来的，以及如果换一个约束条件应该怎么改**。

最后我想把评审文档 6.2 节的那 4 个缺陷留在这里作为提醒：
**其中 3 个是在"系统看起来完全正常"的情况下被自动化测试和门禁脚本发现的。**
如果这个项目只做了一件对的事，那就是——**我们把"看起来没问题"换成了
"退出码是不是 0"。**
